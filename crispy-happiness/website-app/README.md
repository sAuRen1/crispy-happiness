# Центр «Пирамидка» — сайт и админка

Flask-приложение: публичная страница с формой записи + закрытая админка
со списком заявок.

## Быстрый старт (локально)

```bash
cd website-app/backend
python -m venv venv && source venv/bin/activate     # можно и без venv
pip install -r requirements.txt

cp .env.example .env
python -c "import secrets; print(secrets.token_hex(32))"   # вставить в .env как SECRET_KEY
python generate_admin_hash.py                                # вставить вывод в .env как ADMIN_PASSWORD_HASH

python app.py
# открыть http://127.0.0.1:5000, админка — http://127.0.0.1:5000/admin
```

`FLASK_ENV=development` в `.env` включает debug-режим Flask. Больше НИГДЕ,
кроме своей машины, этот режим не включай — см. ниже, почему.

## ⚠️ Если у тебя уже был закоммичен .env или *.db — сделай это в первую очередь

В более старой версии этого репозитория (публичного на GitHub) были
закоммичены: пароль администратора открытым текстом в `app.py`, `.env`
с ключом и `instance/ankety.db` — реальная заявка (имя, email, телефон)
человека, который тестировал форму. Раз репозиторий публичный, эти данные
уже были технически доступны кому угодно.

Что сделать прямо сейчас, по порядку:

1. Обновить `app.py` и шаблоны на версию из этой поставки (пароль теперь
   не хардкодится, а приходит из `.env` в виде хэша).
2. Перестать отслеживать секреты в git:
   ```bash
   git rm --cached website-app/backend/.env
   git rm --cached instance/ankety.db website-app/backend/instance/ankety.db
   git add .gitignore
   git commit -m "Убрать секреты и базу данных из git"
   git push
   ```
3. Считать старый пароль администратора и старый `SECRET_KEY` **скомпрометированными** —
   сгенерировать новые (команды выше) и никогда не использовать прежние значения.
4. (Опционально, но по-хорошему нужно) Эти файлы всё ещё лежат в старых
   коммитах истории GitHub — шаг 2 не удаляет их оттуда, а только
   останавливает отслеживание вперёд. Полностью вычистить историю можно так:
   ```bash
   pip install git-filter-repo
   git filter-repo --path website-app/backend/.env \
                    --path instance/ankety.db \
                    --path website-app/backend/instance/ankety.db \
                    --invert-paths
   git push --force
   ```
   Это переписывает историю и требует force-push — операция необратимая.
   Если репозиторий соло-учебный и его никто больше не клонировал — обычно
   безопасно. Если сомневаешься — можно и не делать: данные уже все равно
   когда-то были в открытом доступе, и как минимум пароль/ключ уже заменены
   на новые в шаге 3, это главное.

## Переменные окружения (`.env`)

| Переменная | Обязательна | Описание |
|---|---|---|
| `SECRET_KEY` | да | Подписывает cookie сессии. `python -c "import secrets; print(secrets.token_hex(32))"` |
| `ADMIN_USERNAME` | нет (по умолчанию `admin`) | Логин администратора |
| `ADMIN_PASSWORD_HASH` | да | Хэш пароля, не сам пароль. Генерируется `generate_admin_hash.py` |
| `FLASK_ENV` | нет (по умолчанию `production`) | `development` — только для локальной разработки |
| `DATABASE_URL` | нет | По умолчанию `instance/ankety.db` рядом с `app.py` |
| `PORT` | нет (по умолчанию `5000`) | Порт для `python app.py` (на проде порт задаёт gunicorn) |

`.env` в `.gitignore` — никогда не коммить этот файл.

## Что уже защищено и почему

- **CSRF-токен** на форме записи и на входе в админку — без него левый сайт
  не сможет отправить запрос от имени залогиненного администратора.
- **Rate limiting** — не больше 5 заявок в минуту и не больше 5 попыток входа
  в админку за 5 минут с одного IP. Хранится в памяти процесса — см.
  ограничение ниже.
- **Honeypot** на форме записи — невидимое людям поле, которое ловит простых
  ботов-заполнителей форм.
- **Пароль администратора — хэш** (`werkzeug` pbkdf2/scrypt), сравнение через
  `check_password_hash`, а не текстовое сравнение.
- **Security headers**: `X-Content-Type-Options`, `X-Frame-Options`,
  `Content-Security-Policy` (запрещает выполнение inline `<script>`),
  `Referrer-Policy`, `Strict-Transport-Security` (вне debug-режима).
- **Cookie сессии**: `HttpOnly` (недоступна из JS), `SameSite=Lax`, `Secure`
  вне debug-режима (передаётся только по HTTPS).
- **SQL-инъекции**: весь доступ к БД идёт через ORM (`SQLAlchemy`/параметризованные
  запросы), нигде нет ручной сборки SQL строками — это уже защищено by design.
- **XSS в админке**: Jinja2 по умолчанию экранирует всё, что выводится через
  `{{ ... }}` — значения из формы (`anketa.name`, `anketa.message` и т. д.)
  не могут быть исполнены как HTML/JS, если только явно не поставить фильтр
  `|safe` (в шаблонах его нигде нет).
- **`MAX_CONTENT_LENGTH`** — сервер отклоняет запросы тяжелее 64 КБ (простая
  форма не должна весить больше).
- **SQLite в режиме WAL** (Write-Ahead Logging) — читатели (например, ты,
  открывший админку) и писатель (кто-то в этот момент отправляет форму) не
  блокируют друг друга. Без этого под нагрузкой запись форму от одного
  человека могла бы на короткое время "подвесить" загрузку списка заявок
  у другого.
- **Логи вместо `print()`** — события уровня WARNING/ERROR (неверный пароль
  админки, сработавший rate limit, ошибка БД) пишутся через `logging`,
  с временем и уровнем важности, а не теряются в консоли. См. раздел
  "Логи" ниже.
- **`/healthz`** — эндпоинт, который реально проверяет соединение с БД, а
  не просто "процесс жив". Хостинг может дёргать его сам и перезапускать
  сайт при 503.
- **Собственные страницы ошибок** (400/404/413/500) — посетитель видит
  оформленную страницу с кнопкой "на главную" вместо голой технической
  заглушки Flask/Werkzeug.

## Известные ограничения — честно, а не "и так сойдёт"

- **Rate limiter и общий счётчик заявок живут в памяти ОДНОГО процесса.**
  Если запустить несколько gunicorn-ВОРКЕРОВ (`--workers 4` — это отдельные
  процессы), у каждого будет своя копия этого словаря, и лимит на практике
  станет мягче в 4 раза. Поэтому ниже рекомендован запуск с одним процессом
  и несколькими ПОТОКАМИ (`--workers 1 --threads N`) — потоки делят память
  процесса, лимитер честный, а сайт всё равно параллельно обслуживает много
  посетителей. Если проект вырастет настолько, что одного процесса будет
  не хватать по CPU (не по числу пользователей — сайт-визитка почти не
  грузит процессор) — тогда лимитер нужно будет переносить на Redis
  (`Flask-Limiter` со `storage_uri="redis://..."`), но для этого масштаба
  это заранее ненужное усложнение.
- **`SESSION_COOKIE_SECURE=True` вне debug** означает, что сайт **обязан**
  открываться по HTTPS в проде — иначе браузер не отправит cookie сессии
  обратно, и вход в админку с формой перестанут работать вообще (не станут
  менее безопасными, а именно перестанут работать). Это осознанно —
  так и должно быть, но не забудь настроить сертификат перед тем, как
  включать `FLASK_ENV=production`.
- CSP разрешает `'unsafe-inline'` для стилей (из-за инлайн `style=""` во
  flash-сообщении в `index.html`) — если захочешь ужесточить дальше, вынеси
  этот стиль в CSS-класс и убери `'unsafe-inline'`.

## Логи

Приложение пишет логи в двух местах одновременно:

- **В консоль (stdout)** — большинство облачных хостингов (Amvera, Timeweb
  Cloud Apps и т. д.) сами ловят то, что процесс печатает в консоль, и
  показывают это в своём разделе "Логи" в панели управления. Отдельно
  ничего настраивать не нужно.
- **В файл** `instance/app.log` (рядом с базой) — на случай, если тебе
  удобнее посмотреть историю локально. Файл сам нарезается на куски по
  1 МБ и хранится не больше 5 последних — старые логи не съедят весь диск.

Уровни: `INFO` — обычные события (сайт запустился, кто-то успешно вошёл в
админку), `WARNING` — что-то подозрительное (неверный пароль, сработавший
rate limit, отклонённый CSRF), `ERROR` — реальная поломка (например, БД
недоступна). Пароли в логи никогда не попадают, даже неверно введённые.

## Автоматические тесты

```bash
cd website-app/backend
python3 -m unittest test_app.py -v
```

Проверяется: форма записи (валидация, honeypot, CSRF, rate limit), вход
в админку (верный/неверный пароль, rate limit, logout), `/healthz`,
кастомная 404-страница, security-заголовки. Тесты создают свою временную
базу данных и не трогают `instance/ankety.db`.

Гоняй эти тесты после любых изменений в `app.py` — они за секунду покажут,
не сломал ли ты что-то из уже работавшего (это и называется
регрессионное тестирование: убедиться, что старое поведение не
"регрессировало", то есть не откатилось назад к багу).

## Деплой на сервер с доменом

Коротко, шаги для обычного VPS (Ubuntu) без привязки к конкретному хостингу:

1. **Код и окружение на сервере**
   ```bash
   git clone <твой репозиторий>
   cd .../website-app/backend
   python3 -m venv venv && source venv/bin/activate
   pip install -r requirements.txt
   cp .env.example .env   # заполнить реальными значениями, FLASK_ENV=production
   chmod 600 .env          # только владелец может читать файл с секретами
   ```

2. **Запуск через gunicorn** (не через `python app.py` — это dev-сервер
   Flask, в логах сам предупреждает, что не для продакшена):
   ```bash
   gunicorn --workers 1 --threads 8 --worker-class gthread \
            --timeout 30 --max-requests 1000 --max-requests-jitter 100 \
            -b 127.0.0.1:8000 app:app
   ```
   Разбор флагов, потому что тут каждый важен:
   - `--workers 1 --threads 8 --worker-class gthread` — один процесс,
     8 потоков внутри него. Для сайта-визитки (простой Flask + SQLite,
     почти вся работа — ждать диск/сеть, а не грузить CPU) это лучший
     вариант: потоки честно делят память (значит rate limiter считает
     правильно, см. выше), а 8 потоков спокойно держат и 100+ человек
     одновременно на сайте, потому что большую часть времени поток не
     "работает", а ждёт ответа диска — в это время он уступает место
     другому запросу. Если увидишь по логам/метрикам, что CPU у сервера
     реально упирается в потолок — тогда можно поднять `--workers` до
     числа ядер, но заодно придётся переносить rate limiter на Redis.
   - `--timeout 30` — если обработка запроса зависла дольше 30 секунд
     (например, что-то заблокировало поток), gunicorn убьёт и перезапустит
     воркер, а не оставит сайт висеть навсегда.
   - `--max-requests 1000 --max-requests-jitter 100` — каждый воркер
     перезапускается сам после ~1000 запросов (плюс-минус 100 случайно,
     чтобы не все воркеры одновременно). Защита от медленных утечек памяти
     за недели работы — дёшево, а подстраховывает.

3. **systemd**, чтобы приложение поднималось само после перезагрузки сервера
   (`/etc/systemd/system/piramidka.service`):
   ```ini
   [Unit]
   Description=Piramidka Flask app
   After=network.target

   [Service]
   User=www-data
   WorkingDirectory=/path/to/website-app/backend
   EnvironmentFile=/path/to/website-app/backend/.env
   ExecStart=/path/to/venv/bin/gunicorn --workers 1 --threads 8 --worker-class gthread --timeout 30 --max-requests 1000 --max-requests-jitter 100 -b 127.0.0.1:8000 app:app
   Restart=always

   [Install]
   WantedBy=multi-user.target
   ```
   ```bash
   sudo systemctl enable --now piramidka
   ```

4. **Nginx как reverse proxy** перед gunicorn (Nginx отдаёт HTTPS, gunicorn
   слушает только `127.0.0.1`, наружу не торчит). Важное отличие от самого
   простого варианта "прокси вообще всё на Flask": картинки, CSS и JS
   отдаёт **сам Nginx напрямую**, а не Flask через gunicorn — Nginx на
   порядок быстрее отдаёт статику (написан на C именно для этого), плюс
   так gunicorn-потоки не тратятся на то, что не требует Python вообще:
   ```nginx
   server {
       listen 80;
       server_name твой-домен.ru;

       # gzip сжимает текстовые файлы перед отправкой браузеру — CSS/JS
       # обычно сжимаются в 3-5 раз, значит настолько же быстрее грузятся
       # на медленном интернете. Картинки (jpg/png) уже сжаты форматом
       # и в список специально не включены — сжимать их ещё раз gzip'ом
       # бессмысленно, только тратит CPU.
       gzip on;
       gzip_types text/css application/javascript application/json image/svg+xml;
       gzip_min_length 512;

       # Статику отдаём напрямую с диска, минуя Flask и gunicorn целиком.
       location /static/ {
           alias /path/to/website-app/backend/static/;
           expires 30d;
           add_header Cache-Control "public, immutable";
           access_log off;
       }

       location / {
           proxy_pass http://127.0.0.1:8000;
           proxy_set_header Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
       }
   }
   ```
   `expires 30d` + `Cache-Control: immutable` означает: браузер посетителя,
   который уже был на сайте, повторно вообще не запрашивает картинки/CSS/JS
   с сервера 30 дней — берёт из своего кэша. Под нагрузкой это резко
   снижает число запросов, которые вообще доходят до сервера.
   `alias` — замени `/path/to/...` на реальный путь на сервере (тот же,
   что в `WorkingDirectory` у systemd-юнита ниже).

5. **HTTPS через Let's Encrypt (certbot)** — обязателен, см. ограничение
   про `SESSION_COOKIE_SECURE` выше:
   ```bash
   sudo apt install certbot python3-certbot-nginx
   sudo certbot --nginx -d твой-домен.ru
   ```
   Certbot сам допишет в Nginx-конфиг `listen 443 ssl` и настроит редирект
   с 80 на 443. После этого проверь, что появился и HTTP/2 (он ускоряет
   загрузку страницы с кучей мелких файлов — ровно наш случай: одна
   главная страница тянет за собой 6 иконок, 2 фото, CSS и JS — HTTP/2
   грузит их все через одно соединение параллельно, а не по очереди):
   ```bash
   sudo nginx -T | grep -A1 "listen 443"
   ```
   Если `http2` в строке нет — допиши вручную в блоке `listen 443 ssl;`
   → `listen 443 ssl; http2 on;` (современный Nginx, ≥1.25) или
   `listen 443 ssl http2;` (более старые версии), затем
   `sudo nginx -t && sudo systemctl reload nginx`.

6. **Файрвол** — открыть только 80/443 и SSH (желательно по ключу, не паролю):
   ```bash
   sudo ufw allow OpenSSH
   sudo ufw allow 'Nginx Full'
   sudo ufw enable
   ```

7. **Проверить нагрузку самостоятельно, а не верить на слово.** После
   того как сайт заработал на реальном домене с HTTPS (шаги 4–5), прогони
   по нему `loadtest_page.py` (передаю отдельным файлом) с любого своего
   компьютера — не с самого сервера:
   ```bash
   python3 loadtest_page.py https://твой-домен.ru 100 150
   ```
   Это симулирует 100 человек, одновременно открывших сайт (главная
   страница + все картинки и стили — 1100 запросов), и покажет реальные
   задержки и коды ответов через настоящую сеть, а не на localhost —
   локальные измерения на такие вопросы честно не отвечают (слишком
   разные условия), поэтому единственная надёжная проверка — на живом
   сервере.

8. **Бэкапы `instance/ankety.db`** — это единственное место, где хранятся
   реальные заявки людей. Простой вариант — ежедневный `cron`, копирующий
   файл в другое место (или в облако):
   ```bash
   0 3 * * * cp /path/to/instance/ankety.db /path/to/backups/ankety-$(date +\%F).db
   ```

## Что сознательно НЕ добавлено — и почему

Два решения, которые я взвесил и осознанно НЕ стал делать, а не забыл:

- **Dockerfile.** Docker — это способ упаковать приложение со всем
  окружением в переносимый "контейнер", который одинаково запускается на
  любой машине. Штука полезная, когда: над проектом несколько человек с
  разными машинами, или деплой идёт на площадку, которая сама требует
  контейнер (например, некоторые PaaS). У нас пока ни того, ни другого —
  ты один, деплоишь на обычный VPS, а шаги 1-6 выше и без Docker дают
  воспроизводимый деплой (venv + systemd). Добавить Docker поверх этого —
  значит выучить ещё один слой понятий (образы, контейнеры, volume для
  базы и бэкапов, сеть между контейнерами) без реальной выгоды на этом
  масштабе. Если в будущем выберешь хостинг, который явно просит
  Dockerfile — тогда добавим его под конкретные требования этого хостинга,
  а не заранее "на всякий случай".
- **Минификация CSS/JS через сборщик (webpack/vite/итд).** У нас один
  CSS-файл (~20 КБ) и один JS-файл (~2.5 КБ) — совсем немного. gzip на
  Nginx (см. шаг 4 выше) уже сжимает текстовые файлы в 3-5 раз без
  дополнительного шага сборки. Отдельный build-pipeline ради ещё нескольких
  КБ экономии на файлах такого размера добавил бы сложность (npm-скрипт,
  зависимость-минификатор, обязательный "не забудь пересобрать перед
  деплоем" шаг, который легко забыть) без ощутимой пользы. Если проект
  вырастет и CSS/JS станут значительно больше — тогда есть смысл вернуться
  к этому вопросу.
